# 业务数据更新与缓存

## 上线顺序

先在 Supabase 应用 `supabase/migrations/20260918000000_business_data_version.sql`，再发布前端。可使用已登录并关联项目的 Supabase CLI（先 `npm run db:push -- --dry-run`），或在目标项目的 SQL Editor 中执行该迁移。不要重新执行整个 `sql/setup.sql`。迁移不修改业务行、邀请码、会话或现有 RLS 策略。随后执行 `sql/check.sql`，确认版本函数与九个触发器通过检查。

2026-09-19 已确认线上版本表存在，并通过九张表的零匹配 UPDATE 验证触发器已生效，没有修改业务行。新环境仍须先迁移、后发布。

## 更新流程

九张业务表（记录、人物、书面页、箴言、补充、资料、隐藏题库、致谢、私有资源元数据）的 INSERT / UPDATE / DELETE / TRUNCATE 在同一事务中递增一个数据库版本。直接 SQL 编辑、管理脚本发布和内容回滚均会触发。事务回滚不发布版本；邀请码、会话和权限表没有这些触发器。

每次完整加载时，统一缓存读取层先等待唯一的版本检查 Promise，再读取业务缓存。多个组件和全局监控共享该检查，最长等待 2.5 秒，失败仍可使用合法缓存。版本相同的数据在原有最长七天保留窗口内复用，不因一天软 TTL 而重复下载。此后每分钟检查一次；页面重新可见、恢复网络或从浏览器历史恢复时也会检查，五秒内合并重复触发。隐藏/离线标签页暂停轮询。版本请求只返回文本计数值，沿用现有邀请码访问检查；不能匿名读取或修改版本表。

版本没有变化时不请求业务表。版本变化时，内存、sessionStorage、IndexedDB 的旧业务缓存按版本失效；挂载中的公共数据 Hook 和 ArchiveProvider 后台重取并原位更新，未打开的页面下次加载时读取新版本。保留筛选、排序、已选资料、题目作答进度和滚动容器；当前正在作答的题目保留快照，后续题目使用更新后的题库。失败时保留已显示内容和错误反馈，每 30 秒重试，避免短暂断网后永久停留在旧数据。

BroadcastChannel 与专用 storage key 将版本传给其他标签页；不支持这两种能力时仍可通过定时检查更新。旧版本/重复通知不重新请求；旧请求结果不能覆盖新版本。

## 明确隔离的状态

- 不调用退出、不清理或替换邀请码凭证、token、权限状态，不改变 90 天滑动期限、365 天绝对期限或撤销处理。
- 同一凭证在其他标签页仅更新验证时间时，不再次触发认证；不同凭证、退出或无效存储仍走原认证流程，避免时间戳互相写回导致循环验证。
- 图片尺寸缓存标记为非业务资源，保留其内存和持久化记录、在途请求、图片签名和已下载原图；静态 Cache Storage、背景配色及偏好不受版本事件影响。
- 图片地址随业务内容变化时按新地址加载；插图在悬停、聚焦或点击时才预读尺寸，已知图片复用原缓存。页面进入与导航悬停不再遍历图片。替换同一路径的二进制内容不属于数据库变更；需要即时更新时应发布新资源路径，避免浏览器继续复用旧图。
- 登出时仍使用原有全站清理流程，它与业务版本失效是不同操作。

## 验证与回滚

`npm test` 包含嵌入式 PostgreSQL 实测：九表增删改/清空、事务回滚、无权限/有效访问、认证表隔离及迁移回滚。缓存测试覆盖内存、持久化、请求去重、版本竞态及图片尺寸保留。

`npm run test:app` 覆盖已打开页面更新、隐藏的第二标签页同步、凭证保留、刷新后仍可访问、无变更时不重读、无认证请求循环、原位更新及图片/静态缓存保留。`npm run test:layout` 覆盖浅深色、四种宽度、公共卡片状态、Star 外部链接及现有布局。

回滚先恢复旧前端，再执行对应 `.down.sql`。只删除版本函数、触发器和版本表，不触及内容与认证。如果曾回滚后重新启用，版本值必须大于曾发布的版本（可在重新应用迁移后将 revision 设为当前 Unix 毫秒数），以保持客户端版本单调递增。
